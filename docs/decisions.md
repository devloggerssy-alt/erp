# Architecture Decisions

## Why Turborepo Monorepo

**Decision**: All apps and packages live in a single pnpm workspace managed by Turborepo.

**Rationale**:
- The API, dashboard, and shared packages (contracts, client, backend-core) are developed together and must stay in sync. A monorepo eliminates versioning friction between packages.
- Turborepo provides task caching (build outputs, type checks, lint results) — with a properly configured remote cache, CI is significantly faster.
- pnpm workspaces with `workspace:*` protocol ensure that all internal packages use the local version, not a published one.
- `check-types` task with `dependsOn: ["^check-types"]` ensures packages are type-checked in dependency order.

**Tradeoffs**:
- Repository is larger and heavier to clone.
- Turborepo's task graph must be kept accurate as new packages are added.

## Why Separate `api-contracts` Package

**Decision**: A dedicated `@devloggers/api-contracts` package holds all resource definitions, DTOs, and OpenAPI-derived types.

**Rationale**:
- **Single source of truth**: API routes, request/response types, and resource keys are defined once. Both the NestJS API and the Next.js dashboard consume them — eliminating drift between frontend expectations and backend implementation.
- **Type safety across the stack**: `defineCrudResource()` produces types that flow through `CrudClient<R>` all the way to React Query hooks on the dashboard.
- **OpenAPI roundtrip**: `openapi-typescript` generates `src/types/` from the running API's Swagger spec. The contracts package is the bridge between runtime API behavior and compile-time frontend types.

**Tradeoffs**:
- Any change to an API route requires regenerating types (`pnpm generate:dev`) and rebuilding `api-contracts` before the dashboard TypeScript compiler picks them up. This adds a step to the development workflow.
- The auto-generated `src/types/` directory cannot be manually edited, which can be surprising.

## Why `CrudService` / `CrudRepository` / `CrudPresenter` Abstractions

**Decision**: Every CRUD resource extends three abstract base classes.

**Rationale**:
- **Eliminates repetition**: Pagination, tenant scoping, `findByIdOrFail`, and event emission are implemented once.
- **Enforces patterns**: Tenant isolation is built into `CrudRepository.findMany()` — developers cannot forget to add `where: { tenantId }`.
- **Hook-based extensibility**: `beforeCreate`, `beforeUpdate`, `beforeDelete` hooks let concrete classes add business rules without modifying the base class (Open/Closed Principle).
- **Separation of concerns**: Repository handles data access; Service handles business rules; Presenter handles serialization. Each is independently testable.

**Tradeoffs**:
- Complex resources that don't fit the CRUD pattern (e.g., `InvoicesService`) have to bypass the base class entirely and use `PrismaService` directly, losing the built-in tenant scoping enforcement.
- The factory pattern (`createCrudController`) requires TypeScript generics — less readable for developers unfamiliar with the pattern.

## Why `generateResource` Compound Component Pattern

**Decision**: Dashboard CRUD pages are composed using a namespace of compound components generated by `generateResource<Client>()`.

**Rationale**:
- **Consistency**: All 25+ resource pages share identical structure (toolbar with filter/search/actions, table with sortable columns, form dialog, pagination).
- **DRY**: Zero duplicated table markup, search debounce logic, or pagination UI across modules.
- **Type safety**: The generic `TClient` parameter flows through the entire component tree — `ResourceItem<TClient>` is inferred correctly for table row types.
- **Extensibility**: Any sub-component (table, toolbar, search) can be replaced independently via explicit `ResourceProvider` + components.

**Tradeoffs**:
- High abstraction level. A developer new to the codebase needs to understand `generateResource`, `ResourceProvider`, `useResourceContext`, and TanStack Table before modifying a resource page.
- The compound pattern can obscure what's actually rendered — `Resource.Page` does a lot implicitly (toolbar, layout, dialogs).

## Why Zod on the Frontend and `class-validator` on the Backend

**Decision**: Two different validation libraries for two different environments.

**Rationale**:
- `class-validator` + `class-transformer` is the NestJS ecosystem standard. The `ValidationPipe` uses it natively. Decorators (`@IsString()`, `@IsNotEmpty()`) work well in a class-based DI system.
- Zod is a better fit for Next.js/React forms: schema definition and type inference in a single expression (`z.infer<typeof schema>`), works with `@hookform/resolvers`, no class instantiation needed.
- Neither library is shared between API and dashboard; the `api-contracts` package provides the bridge at the DTO level.

**Tradeoffs**:
- Two validation approaches to maintain. Schema changes require updates in both the NestJS DTOs and the Zod form schemas.
- No automatic validation parity enforcement between frontend and backend schemas.

## Why Multi-Tenant, Single-Database

**Decision**: All tenants share one PostgreSQL database. Every row is scoped by `tenantId`.

**Rationale**:
- Simpler infrastructure: one DB to manage, backup, and monitor.
- Lower cost at early stage.
- Prisma's ORM layer makes tenant scoping mechanical once the base repository enforces it.

**Tradeoffs**:
- **Data isolation**: A bug in the tenant-scoping logic could expose cross-tenant data. This is the highest-severity risk in the current architecture.
- **Scalability**: Large tenants will share I/O bandwidth with small ones. Noisy-neighbor problems become possible at scale.
- **Migrations**: Schema changes affect all tenants simultaneously. Rolling migrations are harder.
- **Compliance**: For enterprise customers requiring strict data isolation (GDPR, SOC2 with strong tenant boundaries), a shared DB may not be acceptable.
- **Shared DB advisory lock**: The memory notes reference deferred migrations blocked by a shared-DB advisory lock — this is a real operational challenge when running migrations against a live shared database.

## Technical Debt Areas

### 1. Invoices Service Bypasses CRUD Infrastructure
`InvoicesService` does not extend `CrudService`. It uses `PrismaService` directly for complex joins. This means:
- Tenant scoping is done manually (not enforced by `CrudRepository`).
- No automatic event emission for invoice mutations.
- Audit logging for invoices is not wired to the standard `AuditLog` mechanism.

### 2. Role-Based Access Control Not Enforced
The `Role` and `UserRole` models exist but granular permission checks are not applied to controllers. Any authenticated user can perform any CRUD operation on any resource within their tenant.

### 3. Live Credentials in `.env.development`
The development environment file contains actual AWS, Twilio credentials. These should be rotated and the file excluded from version control.

### 4. CORS Allows All Origins
`origin: true` is appropriate for development but must be restricted before production deployment.

### 5. OpenAPI Type Generation Requires Running API
The `pnpm generate:dev` workflow requires the API to be running. This creates a friction point in CI/CD and for new developer onboarding.

### 6. No Soft Delete
All deletes are hard deletes. For an ERP system where data traceability is important (invoices, stock movements, etc.), the lack of soft delete means posted documents can potentially be hard-deleted if the delete endpoint is called on a POSTED entity (though the `beforeDelete` hook can prevent this).

### 7. No Refresh Token Implementation
The JWT refresh token flow is partially configured (env vars exist) but the refresh endpoint and token rotation logic are not implemented.
